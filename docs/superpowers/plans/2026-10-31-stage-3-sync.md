# Stage 3 (Campaign sync) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.
>
> **Execution model (as in stage 2, user request):** tasks are grouped. Each **Group** is ONE implementer dispatch
> (a commit per task) followed by ONE review of the group's diff. The next group may build while the previous one is
> reviewed; fixes wait until the active implementer finishes (one writer at a time). The last group's review may be
> folded into the final whole-branch review.

**Goal:** A DM hosts a campaign from their browser; players join with a code and link; each player's characters sync
both ways with the DM (merging offline edits); players receive the DM's player-facing books and see the party roster
and public rolls; nothing hidden ever leaves the DM's device.

**Architecture:**
- **Merge core (pure):** a hybrid logical clock (HLC) and per-field clocks stored with each synced character. A save
  stamps the paths it changed; merging takes, per path, the value with the later clock. Inventory is a list keyed by
  entry id with add-wins and tombstoned deletes. Same-field conflicts are last-writer-wins by HLC, with no prompt (spec 3.6).
- **Engine (pure, transport-agnostic):** a `Host` (DM) and a `Guest` (player) exchange validated JSON messages over an
  abstract `Link`. Tests run both ends in memory. The host validates shape, ownership and size on every message.
- **Transport:** PeerJS (WebRTC data channels, the public PeerJS signaling server, Google STUN), loaded lazily only when
  hosting or joining. Star network with the DM in the middle.
- **Projection:** everything a player receives is built by pure functions that never include hidden data: the campaign
  for players, roster summaries, `playerCharacter` (stage 1) for their own characters, and packs without monsters.

**Tech Stack:** stage 1–2 stack plus `peerjs@1.5.5` (MIT; lazy chunk).

**Spec:** `docs/superpowers/specs/2026-10-30-dnd-app-design.md` — 2 (roles, player IDs), 3.6 (all of it), 5 (anti-goals:
data loss, leaks), 6 (performance, storage), 8 (PeerJS, sync calls), 9 stage 3, 10 (sync merge must be tested). Rulings
carried from earlier stages: R50 (no "party loot": the DM's Unassigned area is DM-only and is never sent; handing an
item over is a character change), R51 (player views only), R52–R54/R60 (2024 never enters, including through sync),
R6 (private rolls never shown to players).

## Global Constraints

- Everything in the stage 1 and 2 Global Constraints still holds: SRD-only repo; no fetching content sites; `.ts`
  imports; no Vite-only syntax in `src/lib` except `content/srd.ts`; 375 px; labelled controls; no heredocs for
  agents; never copy test data into the repo; the controller pushes by hash.
- **The P2P code loads lazily.** `peerjs` and the engine must not enter the first-load bundle (`npm run size` ≤ 150 KB;
  it is ~44 KB now).
- **Hidden data is never sent** (spec 3.6). That means monsters and monster packs, the DM's own homebrew items and
  monsters (except as player views inside an inventory), the Unassigned area, hidden item fields and redacted text,
  private rolls, and other players' full characters (summaries only). This is enforced in the projection functions,
  with tests that serialize what is sent and search it for the hidden values.
- **The DM's device validates every incoming message:** shape, ownership (a player changes only characters whose
  `ownerId` is their player ID), and size. A message over **256 KB** is dropped and the link closed. A pack chunk is at most
  **64 KB**. A pack over **64 MB** is refused.
- **2024 never enters through sync:** incoming characters go through `strip2024` and `characterProblem`; incoming packs
  through `packAllowed` / `entityAllowed`, as stored packs do.
- Join code: **12 characters**, random (`crypto.getRandomValues`), alphabet `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (no
  0/O/1/I/L). The link is `…/#/join/CODE`. The PeerJS peer id is `dndapp-` + the first 32 hex characters of
  SHA-256(code). The guest's first message must carry the code, and the host rejects any other.
- Player IDs: one letter and one digit, `A1`…`Z9`, the next free in order (A1, A2 … A9, B1 …), unique per campaign,
  never reused after removal.

## Review Focus

1. **Offline edits on two devices of the same player plus the DM**, then everyone reconnects in any order: every
   device converges on the same record, and no edit to a different field is lost (Task 1 property test).
2. **A crafted guest message:** a wrong code, someone else's character, an oversized payload, a malformed shape, a
   2024 entity in a pack or character, or a `__proto__` key. Each is refused, nothing is stored, and the host keeps serving
   everyone else (Task 3).
3. **What a player receives contains no hidden data:** search every serialized outgoing message in a test session for
   a hidden item's real name, a redacted string, a monster name and a private roll (Task 3).
4. **Rotating the join code** disconnects guests on the old code at once, and the old link no longer reaches the host
   (Tasks 3 and 5).
5. **A weak phone with a big pack library:** packs are sent once per content hash and in chunks, with progress. A
   reconnect does not resend packs the guest already has (Task 4).

## Group A — Merge core (Tasks 1–2)

### Task 1: HLC and the character merge

**Files:** create `src/lib/sync/hlc.ts`, `src/lib/sync/merge.ts`; test `tests/sync/merge.test.ts`.

**Interfaces — Produces:**
```ts
// hlc.ts — HLC timestamps as sortable strings: `${wallMs padded to 15}:${counter padded to 6}:${nodeId}`
export type Hlc = string;
export function hlcNow(node: string, last?: Hlc, wall?: number): Hlc;        // max(wall, last.wall); counter bumps on tie
export function hlcReceive(node: string, local: Hlc | undefined, remote: Hlc, wall?: number): Hlc;
export const hlcCompare: (a: Hlc, b: Hlc) => number;                          // total order; node id breaks ties
// merge.ts
export interface SyncMeta { clock: Record<string, Hlc>; gone: Record<string, Hlc> } // path → clock; removed inventory entry id → clock
export type Synced<T> = T & { sync?: SyncMeta };
export function stamp(prev: Synced<Character> | undefined, next: Character, at: Hlc): Synced<Character>;
export function mergeCharacter(a: Synced<Character>, b: Synced<Character>): Synced<Character>;
export const SYNC_PATHS: readonly string[]; // documented list of the tracked paths
```
- **Paths:**
  - Each top-level field is one path (`name`, `details`, `overrides`, `customEffects`, `currency`, `campaignId`, `ownerId`).
  - These are split one level deeper: `build.*` (raceId, levels, choices, …), `state.*` (hp, tempHp, slotsUsed, conditions, …),
    `details.*`, `currency.*`.
  - `inventory` is per entry: `inventory/<entryId>` holds the whole entry (quantity, equipped, etc.). Concurrent changes to
    different entries both survive. Concurrent changes to the same entry are LWW for the entry as a whole.
  - `embedded` is derived from build and the content index: take the record with the newest `build.*` clock.
  - `updatedAt` is not tracked; it is the merge time.
- `stamp` compares `prev` and `next` path by path (deep-equal on JSON) and gives every changed path the clock `at`. An
  inventory entry missing from `next` that was in `prev` gets a `gone[id] = at` tombstone.
- `mergeCharacter`:
  - for each path, the value whose clock is later
  - inventory = the union of entries, minus any entry whose tombstone is later than that entry's own clock (deletions stick),
    with the order kept from the newer record
  - commutative, associative and idempotent
- An unstamped (legacy) record counts as all paths at clock `''`, the smallest.

- [ ] **Step 1: Failing tests.**
  - The spec's three guarantees:
    - device A changes `state.hp` and device B changes `details.notes` → both survive
    - A adds entry x and B adds entry y → both present
    - A deletes x while B changes something else → x stays deleted
    - both change `state.hp` → the later HLC wins, even when B's wall clock is 10 minutes behind but its HLC is later
      because it had received A's earlier change
  - HLC: monotonic under a clock that goes backwards; `hlcReceive` moves past the remote clock.
  - **Review Focus 1, a property test:** 200 random edit scripts over 3 replicas (two player devices and the DM) with
    random merge orders and partial syncs. Every replica converges to an identical record (deep-equal after
    `mergeCharacter` both ways), and merge is idempotent and commutative on every pair. Use a seeded PRNG.
- [ ] **Steps 2–4:** FAIL → implement → PASS.
- [ ] **Step 5: Commit** `feat: hybrid logical clock and field-level character merge`.

### Task 2: Stamping saves and the player projections

**Files:**
- Modify: `src/lib/db.ts` (characters.put stamps), `src/lib/types.ts` (Character gains optional `sync?: SyncMeta`;
  Campaign gains optional `sync?: CampaignSync`), `src/lib/recordShape.ts`
- Create: `src/lib/sync/project.ts`
- Test: `tests/sync/project.test.ts`

**Interfaces — Produces:**
```ts
// types.ts
export interface CampaignSync { role: 'dm' | 'player'; code: string; node: string; last?: Hlc;
  players?: Record<string, { name?: string; removed?: boolean }>; playerId?: string /* role player */; deleted?: Record<string, Hlc> /* character id tombstones */ }
// project.ts (pure)
export interface CampaignForPlayers { id: string; name: string; settings: CampaignSettings; enabledPacks: string[] }
export interface RosterEntry { id: string; ownerId: string; name: string; portrait?: string; race: string; classes: string; level: number; hp: number; maxHp: number; conditions: string[] }
export function campaignForPlayers(c: Campaign): CampaignForPlayers;           // no loot, no sync secrets, no players list
export function rosterEntry(c: Character, index: ContentIndex, settings: CampaignSettings): RosterEntry;
export function packForPlayers(p: Pack): Pack | undefined;                      // drops monster entities and monster patches; undefined if nothing left or !packAllowed
export function characterForPlayer(c: Synced<Character>): Synced<Character>;    // playerCharacter(c) + keeps sync meta; strips nothing else
```
- **Stamping:**
  - `db.characters.put` stamps automatically when the character belongs to a campaign whose `sync` is set. It uses that
    campaign's node id and last clock, then persists the advanced clock.
  - `stamp` runs before `strip2024`'s write, and the write stays one transaction. Characters outside a synced campaign are
    stored as today, unstamped.
  - The node id is a random 8-character id per device per campaign.
- `recordShape` accepts the optional `sync` (and validates it as `{clock: Record<string,string>, gone: Record<string,string>}`).
  Backups carry it.

- [ ] **Step 1: Failing tests:**
  - A put in a synced campaign stamps exactly the changed paths. A put outside one adds no `sync`.
  - `campaignForPlayers` has no `loot` and no `sync`.
  - `packForPlayers` drops monsters and returns undefined for a monster-only pack or an `@XMM` pack.
  - `characterForPlayer` on a character holding a hidden-rarity, cover-named item: `JSON.stringify` contains neither the real
    name nor the redacted text.
  - `rosterEntry` gives name, race, "Fighter 3", level, HP and conditions, and nothing else (exact key set).
- [ ] **Steps 2–4:** FAIL → implement → PASS. Run `npm run check`.

## Group B — Protocol and engine (Tasks 3–4)

### Task 3: Messages, validation, the Host and Guest engine

**Files:**
- Create: `src/lib/sync/protocol.ts`, `src/lib/sync/host.ts`, `src/lib/sync/guest.ts`, `src/lib/sync/link.ts`, `src/lib/sync/code.ts`
- Test: `tests/sync/engine.test.ts`

**Interfaces — Produces:**
```ts
// link.ts
export interface Link { send(msg: unknown): void; onMessage(f: (msg: unknown) => void): void; onClose(f: () => void): void; close(): void; readonly id: string }
export function memoryPair(): [Link, Link];                                     // for tests
// code.ts
export function newJoinCode(): string;                                          // 12 chars, constraint alphabet
export async function peerIdFor(code: string): Promise<string>;                 // 'dndapp-' + sha256 hex[0..32]
export function nextPlayerId(taken: Iterable<string>): string;                  // A1…Z9; throws when full
// protocol.ts — every message: { t: <type>, ... }; parseGuestMessage(raw): GuestMsg | { error }
//   Guest→Host: hello {code, playerId?, name?}, chars {characters: Synced<Character>[]}, deleteChar {id, at}, roll {entry}, packWant {ids}
//   Host→Guest: welcome {playerId, campaign: CampaignForPlayers, roster: RosterEntry[], packs: {id,hash,size}[]}, rejected {reason},
//               chars {characters}, roster {roster}, roll {entry}, packChunk {id, hash, seq, total, data}, settings {campaign}, bye {reason}
export const MAX_MESSAGE = 256 * 1024, MAX_CHUNK = 64 * 1024, MAX_PACK = 64 * 1024 * 1024;
// host.ts
export class Host { constructor(deps: HostDeps); accept(link: Link): void; rotateCode(): Promise<string>; removePlayer(id: string): void;
  broadcastRoll(e: RollEntry): void; characterChanged(id: string): void; stop(): void; readonly players: ReadonlyMap<string, { links: number; name?: string }> }
// guest.ts
export class Guest { constructor(deps: GuestDeps); connect(link: Link): void; characterChanged(id: string): void; sendRoll(e: RollEntry): void; stop(): void;
  readonly status: 'connecting' | 'online' | 'offline' | 'rejected' }
// HostDeps/GuestDeps: db-like adapters (load/save characters, packs, campaign), an index provider, a clock (node + now) — so tests use fakes.
```
- **Join flow:**
  - `hello` with the wrong code → `rejected`, then close.
  - `hello` without a `playerId` → the host allocates `nextPlayerId` and records it in `campaign.sync.players`.
  - `hello` with a known, not-removed `playerId` → welcome as that player, even with several links at once.
  - A removed ID → `rejected`.
- **Characters:**
  - After welcome, the guest sends all its characters for this campaign; the host sends all characters owned by that player.
    Each side merges with `mergeCharacter`, saves, and sends back the merged record if it differs.
  - A save on either side → `characterChanged` sends that record (projected through `characterForPlayer` host-side) to every
    link of the owner. The host also re-broadcasts a roster update to all.
  - A character deletion uses tombstones in `campaign.sync.deleted`.
- **Host validation on every guest message:** `parseGuestMessage` with explicit shapes. Ownership: every character's `ownerId`
  equals the link's playerId and `campaignId` equals the campaign. Then `characterProblem`, `strip2024`, and the size limit.
  On a violation, drop the message, count it, and close that link after 3 violations.
- **Inventory entries:** the host keeps its own `item`, `view` and `sourceId` for entries whose id already exists host-side
  (a player can't rewrite an item definition, R56 logic). Brand-new entries from a player are accepted when `soundItem` passes.
- **Rolls:** a guest's public roll → the host stores it in its log and broadcasts it to all. Private rolls are never sent by
  either side. The host's public rolls are broadcast.
- `rotateCode` sets a new code, closes every link with `bye {reason: 'code changed'}`, and the transport layer re-registers
  under the new peer id (Task 5).

- [ ] **Step 1: Failing tests,** using `memoryPair` and fake deps:
  - a full join of a new player gets A1, and a second player gets A2
  - rejoining as A1 from a second link: both links receive character updates
  - a character edited on the guest offline, and the same character edited on the DM, merge on connect, both ways
  - **Review Focus 2:** wrong code; a character owned by A2 sent from A1; a 300 KB message; `{t:'chars', characters:[{__proto__:{x:1}}]}`;
    a character embedding an `@XPHB` class; a malformed shape. Each is refused, the store is unchanged, and other links keep working.
  - **Review Focus 3:** in a session with a hidden-item character, a DM homebrew monster, an Unassigned item and a private roll,
    no message's JSON contains their real names or text
  - **Review Focus 4 (engine part):** `rotateCode` closes all links, and a `hello` with the old code is rejected
  - `removePlayer` closes that player's links, and their next hello is rejected
- [ ] **Steps 2–4:** FAIL → implement → PASS.

### Task 4: Pack sharing

**Files:** modify `host.ts`, `guest.ts`, `protocol.ts`; test `tests/sync/packs.test.ts`.

- In `welcome`, the host lists the campaign's enabled packs that `packForPlayers` keeps, with content hash and byte size.
- The guest compares hashes with its stored packs and sends `packWant` for the missing or changed ones only.
- The host streams each wanted pack as JSON split into `packChunk` messages of at most `MAX_CHUNK`, one pack at a time, and
  waits for the link's buffer to drain between chunks. The transport exposes `bufferedAmount` or a drain hook; the memory
  link drains at once.
- The guest:
  - reassembles each pack, checks that its hash matches, and parses it
  - accepts it only if `packAllowed` and every entity passes `entityAllowed`
  - stores it as a pack marked `sharedBy: campaignId`, so deleting the campaign can clean it up
  - shows progress through a status callback (packs done / total, bytes)
- A pack over `MAX_PACK`, a chunk out of order, or a hash mismatch → discarded, with an error status.
- The guest's content index for that campaign = SRD + the shared packs. Settings for a player campaign are read-only.

- [ ] **Step 1: Failing tests:**
  - a 3-pack campaign where the guest already has one pack by hash: exactly 2 packs are sent
  - a reconnect sends none (**Review Focus 5**)
  - a monster pack is never listed
  - a tampered chunk → hash mismatch → not stored
  - a pack containing a `@XMM` entity → refused
  - chunk sizes stay ≤ 64 KB
- [ ] **Steps 2–4, then commit** `feat: share player-facing packs by content hash`.

## Group C — Transport and UI (Task 5)

### Task 5: PeerJS transport, hosting and joining, roster and shared rolls

**Files:**
- Create: `src/lib/sync/peer.ts` (PeerJS adapter → `Link`), `src/lib/sync/session.svelte.ts` (the app-wide session store:
  starts, stops and resumes the host or guest, and exposes status, players and errors), `src/ui/sync/HostPanel.svelte`,
  `src/ui/pages/Join.svelte`, `src/ui/sync/Roster.svelte`, `src/ui/sync/SyncStatus.svelte`
- Modify: `package.json` (add `peerjs@1.5.5`), `src/App.svelte` (route `join/:code`; status chip in the header),
  `src/ui/pages/CampaignSettings.svelte` (Host panel), `src/ui/pages/Characters.svelte` (roster section for a synced
  campaign), `src/ui/DiceTray.svelte` (rolls from others, labelled with the player ID/character name), `src/lib/rolls.svelte.ts`
  (a hook so new public rolls go to the session)
- Test: `tests/sync/session.test.ts` (session logic with a fake transport)

- **Transport:**
  - PeerJS with its default public signaling server and `iceServers: [{ urls: 'stun:stun.l.google.com:19302' }]`.
  - Data channels are reliable, JSON serialization.
  - `peer.ts` maps a PeerJS `DataConnection` to `Link`. It enforces `MAX_MESSAGE` on receive before parsing (string length
    check), and exposes `bufferedAmount` for Task 4's drain.
  - The DM registers as `peerIdFor(code)`; a guest connects to it with a random peer id.
  - Reconnect with backoff (2 s, 5 s, 15 s, then every 30 s) while the page is open.
- **Host (DM, in campaign Settings):**
  - "Host this campaign" generates the code (stored in `campaign.sync`) and shows the code and the link, with Copy
    buttons.
  - It lists the players: ID, name, characters, online/offline.
  - It offers Remove player, and **Issue a new join code**, with a confirm saying who will be disconnected.
  - Hosting resumes automatically when the DM opens the app with that campaign selected; a header chip shows "Hosting · 2
    online".
  - "Stop hosting" stops it until the DM hosts again.
  - Known-limit help text: "Players on the same Wi-Fi connect reliably; some mobile and school networks block direct
    connections."
- **Join (player):**
  - `#/join/CODE` shows "Join as a new player" (with an optional display name) and "I already have a player ID" (an ID input).
  - On welcome it creates or updates the local campaign: same id as the DM's, `sync.role = 'player'`, the received name and
    settings.
  - It then shows pack download progress and goes to Characters.
  - New characters made in that campaign get `ownerId = playerId`.
  - The player's campaign Settings are read-only, with "Settings are set by your DM".
  - Leaving the campaign is the existing delete.
- **Roster:** in a synced campaign, the Characters page shows the party, for the DM and for players. Players see other
  characters as summaries only: name, portrait, race, class and level, an HP bar and conditions, with no sheet link. The DM
  sees full links to every character.
- **Shared rolls:** public rolls go to the session. Received rolls appear in the tray labelled by player and character.
  The R6 privacy rules stay.
- **Lazy loading:** `session.svelte.ts` imports the engine and `peer.ts` dynamically when hosting or joining starts.
  First load stays ≤ 150 KB.
- **Browser check (required):**
  - Run the dev server, then open two tabs in the browser pane: one as DM, the other on a separate origin profile if
    possible. Otherwise use a second browser context or `127.0.0.1` vs `localhost`, so IndexedDB differs.
  - The DM hosts; the other tab joins via the link as A1, creates a character, and sees it on the DM side.
  - The DM changes that character's HP, and it updates on the player.
  - A public roll on the player shows on the DM.
  - A hidden-rarity item handed to the character shows only its player view on the player tab.
  - Rotating the code disconnects the player (**Review Focus 4**), and the old link fails.
  - If the public signaling server is unreachable, say so and cover the flow with the fake-transport tests.
